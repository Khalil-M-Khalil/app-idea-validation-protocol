# Contributing Guidelines

Thank you for your interest in improving the **App Idea Validation Protocol**.

This project provides an evidence-based, disciplined framework for validating digital product and mobile application ideas. We welcome contributions that improve evidentiary standards, update market benchmarks, refine validation heuristics, or fix documentation errata.

---

## 1. Principles for Contributions

When proposing changes, adhere to the core philosophy:
- **No Speculative Claims:** Every addition of a market figure, benchmark, or threshold must cite a credible, identifiable source and date.
- **Evidence Hierarchy:** Maintain strict separation between `مشاهَد` (Observed Fact), `استنتاج` (Inference), and `فرضية` (Hypothesis).
- **Preserve Core Logic:** Do not dilute decision gates into vague suggestions. The value of this framework lies in its decisive Continue / Pivot / Kill boundaries.
- **Dual Language Integrity:** If modifying core concepts, ensure updates are reflected accurately in both English documentation and Arabic reference files.

---

## 2. Types of Contributions We Welcome

1. **Benchmark & Source Refreshes:** Updating annual market intelligence reports (e.g., RevenueCat, Sensor Tower) with verified current data.
2. **Platform Policy Corrections:** Updating app store developer fees, testing requirements, or compliance guidelines as Apple or Google update their terms.
3. **Decision Gate Heuristics:** Documenting calibrated thresholds for specialized niches (e.g., enterprise B2B SaaS vs. consumer iOS utilities).
4. **Documentation & Formatting:** Fixing typos, broken links, unclear phrasing, or markdown formatting issues.

---

## 3. Pull Request Process

1. **Fork & Branch:** Create a feature branch with a descriptive name (e.g., `update-2027-store-policies` or `fix-markdown-anchors`).
2. **Verify Links & Frontmatter:** Ensure all internal relative links resolve correctly and `SKILL.md` frontmatter remains valid YAML.
3. **Document Sources:** If adding statistics, include direct URLs, report titles, and measurement dates in your commit message or PR description.
4. **Clear Commit Messages:** Use concise, conventional commit prefixes (e.g., `docs:`, `fix:`, `feat:`, `refactor:`).
5. **Submit PR:** Use the provided Pull Request template and explain the motivation and supporting evidence for your change.

---

## 4. Code of Conduct

We are committed to maintaining a professional, respectful, and evidence-driven collaboration environment. Respect differing technical viewpoints and focus discussions on empirical data and practical utility.
